## Что такое модуль в Python
**Модуль** — это обычный Python-файл (`.py`), который содержит функции, классы или переменные, и который можно **импортировать** в другие части программы.  
Он помогает разбивать код на **логические части** и **повторно использовать** уже написанные компоненты.

Например:
```python
# text_utils.py
def count_words(text):
    return len(text.split())
```

Теперь этот файл можно использовать как модуль:
```python
import text_utils

print(text_utils.count_words("Привет мир"))  # 2
```
Такой способ импорта отлично работает, если проект небольшой и состоит из пары файлов.
Но что, если у нас десятки модулей, сгруппированных по темам — например, обработка текста, файловые конвертеры и т.д.? (`../lab05/json_csv.py` и `../lib/text.py`)

Тогда логично объединить их в **пакеты**. Пакет — это не один файл, а целая папка с несколькими связанными модулями. Для этого был придуман ⬇

## `__init__.py`. Что он делает и зачем он нужен?

Чтобы Python понял, что перед ним **пакет**, а не просто папка,  
в ней должен быть файл `__init__.py`.  
Он может быть пустым — достаточно просто его наличия.  
Этот файл говорит интерпретатору:  
> «Эта директория — часть Python-проекта, и из неё можно импортировать модули».

Пример структуры:
```
src/
└─ lib/
   ├─ __init__.py
   └─text.py
```

Теперь можно импортировать код сразу из пакета:

```python
from src.lib import text
from src.lib.text import normalize
```

Таким образом, `__init__.py` превращает набор отдельных модулей в **единую библиотеку**,  
из которой можно удобно импортировать нужные части.  
Если его убрать, Python не будет считать папку пакетом, и импорт из неё перестанет работать.

## Что такое Python-проект

Когда модули и пакеты объединяются в одну логическую систему, получается **Python-проект**.  
Это уже не просто набор скриптов, а структурированное приложение, в котором:
- есть исходный код (`src/` или `app/`),
- тесты (`tests/`),
- данные или примеры (`data/`),
- документация и вспомогательные файлы (`README.md`, `requirements.txt` или `pyproject.toml`).

Такой проект можно:
 - Установить
 - Запустить
 - Протестировать
 - Упаковать в библиотеку или даже опубликовать.

Главная идея — код должен быть **самодостаточным и воспроизводимым**:  
любой человек, скачавший репозиторий, сможет запустить всё теми же командами на любой машине.

Пример структуры минимального Python-проекта:
```
project_name/
├─ src/
│  └─ lib/
│     ├─ __init__.py
│     └─ text.py
├─ tests/
│  └─ test_text.py
├─ data/
│  └─ samples/
├─ README.md
└─ pyproject.toml
```

В этой структуре нам уже всё знакомо, кроме `pyproject.toml`. Что это такое? ⬇


## Что такое `pyproject.toml`

`pyproject.toml` — это **единый конфигурационный файл Python-проекта**.  
Он используется для описания:
- метаданных проекта (название, версия, автор);
- зависимостей;
- конфигурации инструментов: `black`, `pytest` и т.д.;
- сборки проекта.

Формат TOML — читаемый, похож на ini, но современнее.
Краткий экскурс по необходимым блокам `pyproject.toml`, чтобы успешно описать проект:

#### Объявление сборки
```toml
[build-system]
requires = ["setuptools >= 77.0.3"]
build-backend = "setuptools.build_meta"
```
Обычно вы просто копируете то, что предлагается в документации к бэкенду сборки. Значения для некоторых распространённых бэкендов сборки можно посмотреть в документации. Один из самых распространенных – **setuptools**

#### Метаданные проекта 

Имя
```toml
[project]
name = "spam-eggs"
```
Версия 
```toml
[project]
version = "2025.0.0"
```
Чаще всего указывается как динамическое поле `dynamic = ["version"]`, чтобы не было ручной поддержки версий.

#### Зависимости

Этот блок делится на две части: **необходимые**(runtime-зависимости) и **опциональные**(optional) зависимости. Для объявления **опциональных зависимостей**:
```toml
[project.optional-dependencies]
dev = [
  "pytest>=8.0",
  "pytest-cov>=5.0",
  "black>=24.0",
  "ruff>=0.6"
]
```

Для **runtime-зависимостей** пишем:
```toml
dependencies = [
  "requests>=2.32",
  "pandas>=2.2"
]
```

Таким образом, один pyproject.toml заменяет кучу отдельных конфигов
(setup.cfg, pytest.ini, .flake8, requirements.txt и т.д.).

## Что такое **тестирование** 
**Тестирование** — это практика проверки программы на соответствие ожидаемому поведению. Мы формулируем **ожидания** (инварианты, контракты) и автоматически проверяем, что код им удовлетворяет.  

Типы (в рамках курса):
- **Unit-тесты:** проверяют отдельные функции и классы.
- **Интеграционные тесты (базово):** проверяют, как части работают вместе.
- **Покрытие кода:** метрика того, какая доля строк была исполнена тестами.

Для реализации тестов в **python** был разработан ⬇

### `pytest`

**pytest** — это **фреймворк** (набор правил, инструментов и расширений) для написания и запуска тестов в Python.  

Ключевые идеи:
- тест — это обычная функция, имя которой начинается на `test_`;
- проверки пишутся обычным `assert`;
- удобная **параметризация** и **фикстуры** (`tmp_path`, `monkeypatch`, и др.);
- экосистема плагинов: `pytest-cov` (покрытие), `pytest-xdist` (параллельный запуск) и т.д.

Минимальный пример:
```python
# tests/test_math.py
def add(a, b):
    return a + b

def test_add():
    assert add(2, 3) == 5
```
Запуск:
```bash
pytest -q
```

Такая команда сама найдет папку `tests` и запустит все файлики в ней имя которых начинается с `test_`.

--- 

### Запуск тестов в CLI

Без конфигов, напрямую из терминала:
```bash
# Запуск всех тестов
pytest

# Короткий вывод
pytest -q

# С покрытием (нужен плагин pytest-cov)
pytest --cov=src --cov-report=term-missing

# Запустить тесты в конкретном файле/классе/функции
pytest tests/test_text.py
pytest tests/test_text.py::TestNormalize
pytest tests/test_text.py::test_tokenize_basic
```

### Как запускать тесты, установив зависимости из `pyproject.toml`

Если у проекта есть `pyproject.toml` с dev-зависимостями, например:
```toml
[project.optional-dependencies]
dev = [
  "pytest>=8.0",
  "pytest-cov>=5.0",
  "black>=24.0",
  "ruff>=0.6"
]
```
то порядок действий такой:

1) **Установить проект (локально) и dev-зависимости**
```bash
# Рекомендуется из чистого виртуального окружения
python -m venv .venv && source .venv/bin/activate  # Windows: .venv\Scripts\activate

# Установить проект (editable) + dev-инструменты
pip install -e ".[dev]"
```

2) **Запускать pytest как модуль из установленного окружения**
```bash
python -m pytest -q
# или просто
pytest -q
```

3) **(Опционально) Запуск с покрытием**
```bash
pytest --cov=src --cov-report=term-missing -q
```

Почему так удобно:
- все инструменты и их версии **задекларированы** в одном месте (`pyproject.toml`);
- команда `pip install -e ".[dev]"` быстро поднимает одинаковое окружение у всех;

### Памятка по разработке тестов
- **AAA-паттерн:** Arrange (подготовка) → Act (действие) → Assert (проверка).
- Именуйте тесты понятно: `test_<что_проверяем>_<какой_случай>`.
- Маленькие тесты > один большой тест. Проще локализовать ошибки.
- Используйте `@pytest.mark.parametrize` для таблиц входов/ожиданий.
- Файлы и каталоги — через фикстуры `tmp_path` / `tmp_path_factory`.

### Параметризация

**Параметризация** — это способ запустить **один и тот же тест** много раз с разными входными данными и ожидаемым результатом.

Вместо:
```python
def test_add_1():
    assert add(1, 2) == 3

def test_add_2():
    assert add(10, 5) == 15

def test_add_3():
    assert add(-1, 1) == 0
```

Принято писать **одну** функцию и набор данных:
```python
import pytest

@pytest.mark.parametrize(
    "a, b, expected",
    [
        (1, 2, 3),        # 1 + 2 = 3
        (10, 5, 15),      # 10 + 5 = 15
        (-1, 1, 0),       # -1 + 1 = 0
    ],
)
def test_add(a, b, expected):
    assert add(a, b) == expected
```

pytest сам прогонит `test_add` три раза:
с `(1, 2, 3)`, потом `(10, 5, 15)`, потом `(-1, 1, 0)`.

Если наша функция подразумевает не элементарное действие в один шаг, а набор действий с предобработкой данных или выводом результата в директорию/файл пишутся  ⬇

### Фикстуры

**Фикстура** — это функция, которую pytest вызывает **до теста** (или после), чтобы подготовить окружение:
 - создать временный файл или директорию;
 - подготовить тестовые данные;
 - открыть подключение к базе (в больших проектах);
 - настроить объект / состояние.

Фикстура помечается декоратором `@pytest.fixture`, а потом её просто **подставляют по имени** в аргументы теста.

Простейший пример:

```python
import pytest

@pytest.fixture
def sample_text():
    return "Привет, мир"
```
Теперь любой тест, у которого в параметрах есть `sample_text`, автоматически получит это значение:

```python
def test_len(sample_text):
    assert len(sample_text) > 0
```
pytest увидит имя `sample_text`, найдёт фикстуру с таким именем, вызовет её и подставит возвращённое значение в тест.

### Фикстура для файловой системы

В pytest есть **встроенные фикстуры**, напр. `tmp_path `— это временная директория для теста.
Допустим, у нас есть функция, которая записывает текст в файл:

```python
# src/lib/files.py
def save_text(path, text: str):
    with open(path, "w", encoding="utf-8") as f:
        f.write(text)
```
Тест с использованием  `tmp_path`:

```python
# tests/test_files.py
from src.lib.files import save_text

def test_save_text(tmp_path):
    file_path = tmp_path / "sample.txt"

    save_text(file_path, "hello")
    content = file_path.read_text(encoding="utf-8")

    assert content == "hello"
```

Здесь:
 - `tmp_path` — уже готовая временная директория (фикстура pytest);
 - мы создаём путь `tmp_path / "sample.txt"`;
 - после теста pytest сам всё почистит.



### Коротко: Фикстура vs Параметризация 

**Параметризация — это данные для теста.**

Параметризация (`@pytest.mark.parametrize`) — это способ передать в тест **конкретные входные данные**, чтобы прогнать один тест несколько раз.

**Фикстура — это подготовка окружения.**

Фикстура (`@pytest.fixture`) — это функция, которая что-то готовит перед тестом:
 - создаёт временную директорию;
 - открывает соединение;
 - генерирует тестовый файл;
 - подготавливает базовый объект: "hello world" или сложную структуру.

## **СТИЛЬ**

`Стиль – это ответ на всё. Свежий подход ко скучному или опасному.
Лучше скучное, но стильное, чем опасное но не стильное.
Опасное и стильное – это искусство. `

Соблюдая стиль при разработке проекта, мы гарантируем, что при появлении второго разработчика, код не перестает быть читаем. 
При написании проекта всегда важно, чтобы код был **одинаково оформлен**:
- одинаковые отступы;
- понятные переносы строк;
- одинаковые кавычки;
- предсказуемые правила «где пробел, а где нет».

Это даёт:

- **Читаемость:** не нужно вникать в чужой стиль — всё единообразно.
- **Меньше споров в ревью:** форматирование решает инструмент, а не «кто громче».
- **Чище git-диффы:** меняется логика, а не пробелы/отступы.

В Python формальные рекомендации по стилю описаны в PEP 8, но руками соблюдать их тяжело.  
Поэтому и появился инструмент  ⬇

## `black`

**`black`** — это автоформаттер для Python-кода.

Основные идеи:
- у вас **мало или нет настроек**;
- на один и тот же код `black` всегда выдаёт **одинаковый результат**;
- вы перестаёте думать о стиле и просто пишете код, а форматированием занимается инструмент.

Упрощённо:  
> «Пишите как хотите — `black` потом приведёт всё к единому виду».

### Два основных режима работы: форматирование и проверка

#### 1. Форматирование кода (изменяет файлы)
Команда:

```bash
black .
```

что делает:
- рекурсивно проходит по текущей директории,
- находит Python-файлы,
- **перезаписывает** их в отформатированном виде.

После этого код в репозитории уже приведён к стилю `black`.

Можно форматировать отдельный файл или папку:
```bash
black src/
black src/lib/text.py
```

#### 2. Проверка без изменений (`--check`)

Команда:

```bash
black --check .
```

что делает:
- проверяет, **нужны ли изменения**, но **не правит** файлы;
- выходной код 0 — всё уже в стиле `black`;
- выходной код ≠0 — есть файлы, которые были бы изменены.

> «Работа принимается, если `black --check .` не выдаёт ошибок».

---

### Как `black` меняет код (интуитивно)

Примеры изменений:

```python
# Было
def add(a,b): return a+b

# Стало
def add(a, b):
    return a + b
```

```python
# Было
numbers=[1,2,3,4,5]

# Стало
numbers = [1, 2, 3, 4, 5]
```

## `black` и `pyproject.toml`

В учебном проекте мы часто добавляем его в dev-зависимости в `pyproject.toml`, чтобы все ставили одну и ту же версию:

```toml
[project.optional-dependencies]
dev = [
  "black>=24.0",
]
```

Хотя в ЛР можно обойтись чисто CLI-командами, в реальных проектах часто настраивают `black` через `pyproject.toml`:

```toml
[tool.black]
line-length = 88
target-version = ["py311"]
extend-exclude = '''
(
  ^\.(venv|env)/|
  ^data/|
  ^images/
)
'''
```

Это позволяет:
- централизованно задать длину строки;
- исключить директории с данными, виртуальными окружениями, картинками;
- разделить «рабочий» код и артефакты.

Но ключевая мысль:
> Даже без конфигов достаточно двух команд: `black .` и `black --check .`.
